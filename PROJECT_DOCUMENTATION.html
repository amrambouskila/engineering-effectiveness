Overview — what this is & why

A single-purpose tool that turns ten raw facts about each delivered project into a five-axis radar of team capability — every number traceable to an input field, a formula, and a tunable constant.

The Effectiveness Radar answers one question: how capable is this engineering team at delivering? It refuses to answer it with surveys, manager gut-feel, or performance reviews. Instead, each completed project contributes exactly 10 input fields (dates, revenue figures, security counts, phase counts, dependency counts), and a deterministic scoring engine transforms them into five composite axes, each scored 0–100 and classified into a HIGH / MID / LOW tier.

The core philosophy, stated in CLAUDE.md section 0: "This is a measurement framework, not an opinion tool. If a score cannot be explained by pointing to an input field, a formula, and a constant, it does not belong." Every formula is documented in the master plan, every constant lives in one named-constant file, and the math is implemented as pure functions so it can be re-implemented identically in Python in a later phase.

This is a phased, multi-session project. The repo currently targets Phase 1 — Frontend MVP: a React 18 + TypeScript-strict app with a Chart.js radar, manual data entry, client-side scoring, and localStorage persistence. Phases 2–5 add a FastAPI + PostgreSQL backend, Jira/security/finance connectors, historical trends, and full automation. The data contracts defined now are designed to become the Phase 2 API and database schema verbatim.

Key concept
The radar is a function of what actually happened, not what people felt happened. Scores are team-level, never individual. The tool deliberately does not track tasks, run sprints, or do performance reviews — it has exactly one job: produce the radar.
What is built vs. what is planned
As of v0.2.0, the scoring engine, type contracts, Zustand store, and unit tests are complete and passing. The UI is not yet built — frontend/src/App.tsx is still a placeholder shell ("Phase 1 — Frontend MVP" heading). The radar chart, data-entry form, project table, and derivation panel described in the plan are next on the roadmap, not yet implemented in the TypeScript app. The original effectiveness.jsx prototype contains a working (SVG-based) version of all of these as a reference. This document marks planned-vs-built explicitly throughout.

Architecture

Phase 1 is a fully client-side pipeline: raw project data → Zustand store → pure scoring functions → (planned) radar + panels. No network, no backend.

Current (Phase 1) topology

The architecture has three clean layers, all inside frontend/src/:

Data layer
The Zustand store projectStore.ts holds an array of ProjectData plus a selectedProjectId. Persistence is automatic via Zustand's persist middleware (localStorage). This is the only stateful, side-effectful module.
Compute layer
The scoring engine under utils/scoring/ is a set of pure, side-effect-free functions. Given inputs it returns numbers. It does not read the store, the DOM, or the network. This is what makes it testable against analytical values and portable to Python.
Presentation layer
React components (currently only the placeholder App.tsx) render the store + scores. Chart logic is meant to be isolated behind a single radar component so a chart-library swap touches nothing else.

Full target architecture (Phases 2–5)

The master plan paints the eventual system: web/mobile/embeddable clients → API gateway + auth → ingestion / scoring / comparison / trend / alert services → Postgres + Redis + queue, fed by Jira / ADO / SonarQube / Snyk / Looker connectors.

10 raw fields→store→per-project scores→aggregate→radar + panels

Core modules — the scoring engine

The heart of the project. Every module here is a pure function with one job, living in its own file under frontend/src/utils/scoring/. All return integers via Math.round and clamp to 0–100.

Constants scoringConstants.ts

The single home for every tunable number — there are no magic numbers anywhere else in the engine. These are the calibration knobs the master plan discusses tuning per-organization.

frontend/src/utils/scoring/scoringConstants.tsAll 14 tunable constants. Phase 2 Python engine must use identical values.
Tip
To recalibrate the radar for a stricter or looser culture, this is the only file you touch. See the calibration table in Roadmap / the master plan for what each constant does.
clamp clamp.ts

The shared bounding helper used by every axis to keep scores inside [min, max].

frontend/src/utils/scoring/clamp.tsMin/max bounding. Imported by all 5 axis calculators.
Speed calculateSpeed.ts

Measures: delivery punctuality. Inputs: target + actual delivery dates (ISO strings). It computes slip days, scales by plannedDuration and the sensitivity multiplier, and inverts so on-time/early = 100.

Implementation diverges from the spec
The master plan / CLAUDE.md §5 define plannedDuration = daysBetween(projectStartBaseline, targetDate) (variable per project, e.g. the effectiveness.jsx prototype uses a hardcoded 2024-06-01 baseline). The current TS implementation instead uses a fixed 180-day planned duration for every project — Math.max(180, 30) always evaluates to 180, and targetDeliveryDate is never used to compute duration (only to compute slip). This is a documented Phase-1 simplification (CLAUDE.md §5 note), but it means Speed currently ignores how long each project was actually scheduled for. To make it per-project, reintroduce a baseline/start date into ProjectData and compute daysBetween(baseline, targetDeliveryDate).
frontend/src/utils/scoring/calculateSpeed.tsSlip-day scoring with local daysBetween helper (rounds ms→days).
Accuracy calculateAccuracy.ts

Measures: how closely the outcome matched the plan, financially and in scope. Inputs: expected/actual revenue, expected/actual phases. It is a 50/50 blend of revenue accuracy and phase accuracy, each clamped to 0–100.

frontend/src/utils/scoring/calculateAccuracy.tsRevenue + phase accuracy blend. Math.max(expectedPhases,1) guards divide-by-zero.
Defense calculateDefense.ts

Measures: security posture weighted by stakes. Inputs: vulnerability count, expected breach cost. Each vuln costs 18 points; if there is at least one vuln, the breach cost (normalized by $500k) amplifies the penalty. This asymmetry is deliberate: a vuln on a high-breach-cost system hurts more.

frontend/src/utils/scoring/calculateDefense.tsVuln penalty + breach-cost amplifier. Breach penalty only applies when vulns > 0.
Strength calculateStrength.ts

Measures: raw value delivered vs. promised — the simplest axis. Inputs: expected/actual revenue. Over-delivery caps at 100; under-delivery scales linearly.

frontend/src/utils/scoring/calculateStrength.tsRevenue ratio × 100, clamped. No external constants.
Endurance calculateEndurance.ts

Measures: compound effect on future delivery. Inputs: reusable components, intersecting projects. Two halves (max 50 each) that sum: reuse capped at 8 components, cross-pollination capped at 5 intersections.

frontend/src/utils/scoring/calculateEndurance.tsReuse + cross-pollination, each half-weighted to 50 points.
Overall & Tier calculateOverall.ts · classifyTier.ts

Overall is the unweighted mean of all five axes (rounded). Tier maps any 0–100 score to HIGH (≥75) / MID (≥45) / LOW (else).

frontend/src/utils/scoring/calculateOverall.ts5-axis mean. Kept as a named function so Phase 4 can introduce weights.
frontend/src/utils/scoring/classifyTier.tsThreshold classifier returning Tier.
Compute orchestrators computeProjectScores.ts · computeAggregateScores.ts

computeProjectScores is the one place that calls all five axis functions for a single ProjectData and wraps the result in a ProjectScores (scores + overall + tier). computeAggregateScores takes an array of ProjectScores, averages each axis across projects (rounded), then recomputes overall + tier on the averaged scores. The zero-project case returns an all-zero LOW aggregate.

Aggregation order matters
Aggregate axes are averages of already-rounded per-project axis scores, and aggregate overall is computed from those averaged axes — not from per-project overalls. This matches the master-plan formula axisAggregate = round(sum(perProjectScores[axis]) / projectCount).
frontend/src/utils/scoring/computeProjectScores.tsSingle-project orchestrator → ProjectScores.
frontend/src/utils/scoring/computeAggregateScores.tsTeam-level averaging → AggregateScores; handles empty input.
State store stores/projectStore.ts

The only stateful module. A Zustand store holding the project array + selected id, with CRUD actions and automatic localStorage persistence. Deleting the selected project clears the selection.

frontend/src/stores/projectStore.tsZustand + persist middleware; localStorage key ee-project-store.
Scores are not stored
The store holds only raw ProjectData. Scores are derived on demand by the compute functions — there is no scores slice to keep in sync. When the UI is built, scores should be memoized selectors over the store, not persisted state.

Scoring formulas & key logic

The exact math, in plain language and as implemented. Every formula is the source of truth that the Phase 2 Python engine must reproduce identically. All axes round to integers and clamp to 0–100.

AxisFormulaBehavior
Speed clamp(100 × (1 − (slipDays / plannedDuration) × 2.5))
slipDays = max(0, daysBetween(target, actual))		 On-time/early = 100. A slip of 40% of planned duration zeroes the score. plannedDuration is fixed at 180 days in the current code.
Accuracy 0.5 × revAcc + 0.5 × phaseAcc
revAcc = clamp(100 − |1 − actR/expR| × 200)
phaseAcc = clamp(100 − |actP−expP|/max(expP,1) × 150)		 Revenue + scope discipline weighted equally. A 50% revenue miss drops revAcc to 0.
Defense clamp(100 − vulns×18 − (vulns>0 ? breachWeight×10 : 0))
breachWeight = breachCost / 500000		 ~5–6 vulns alone zero the score; breach cost amplifies. No penalty amplification at zero vulns.
Strength clamp(actR / max(expR,1) × 100) Linear value delivery; over-delivery caps at 100.
Endurance clamp(reusable/8 × 50, 0, 50) + clamp(intersects/5 × 50, 0, 50) Two 50-point halves: reuse (cap 8) + cross-pollination (cap 5).
Overall round((spd+acc+def+str+end) / 5) Unweighted mean (Phase 1). Weighting deferred to Phase 4.
Tier score≥75 → HIGH · score≥45 → MID · else LOW Boundary-inclusive thresholds.

Worked example — Speed

From the unit test in calculateSpeed.test.ts: a project targeting 2025-06-01 delivered 2025-07-01 is 30 days late. With plannedDuration = 180: 100 × (1 − (30/180) × 2.5) = 100 × (1 − 0.4167) = 58.33 → 58. A project 80 days late goes negative and clamps to 0.

Key concept — defensibility
Every score on the radar can be traced backward: an axis value → its formula → the specific input fields and named constants. There is no place in the engine where a number appears without provenance. That is the entire point of the project.

How to run it

Two paths: local dev with pnpm + Vite, or Docker via the launcher script. Both expose the app on port 5230.

Local dev (no Docker)

  1. cd frontend
  2. pnpm install — installs deps from pnpm-lock.yaml.
  3. pnpm dev — Vite dev server at http://localhost:5230.
  4. pnpm lint · pnpm test · pnpm build as needed.

Docker (launcher)

  1. Run run_engineering_effectiveness.sh (macOS/Linux) or run_engineering_effectiveness.bat (Windows).
  2. The script runs docker compose up --build -d, waits for http://localhost:5230 to respond, then opens it.
  3. At the menu, pick: k stop (keep image) · q stop + remove image · v stop + remove image + volumes · r full restart (rebuild + relaunch).

Or directly: docker compose up --build from the repo root (see docker-compose.yml).

What you see today

How to edit / extend it

Owner-focused playbook: where each kind of change lives and the files you touch. The golden rule from CLAUDE.md: re-read CLAUDE.md + the master plan + docs/status.md before any change, and keep one concept per file.

Recalibrate the scoring (change sensitivity)

Edit only scoringConstants.ts. Change a constant (e.g. SPEED_SENSITIVITY_MULTIPLIER from 2.5 → 2.0 to be more forgiving). Then update the affected unit tests' expected values, and document the change in docs/versions.md + the master plan's calibration table. No formula file changes.

Add or change an axis formula

Edit the relevant calculate*.ts file (e.g. calculateDefense.ts). Keep new numbers as named constants in scoringConstants.ts — never inline literals. Add/update the matching test under frontend/tests/unit/scoring/ with an analytical expected value. Mirror the formula change in CLAUDE.md §5 and the master plan (these are the cross-language source of truth).

Fix Speed's planned-duration first if you touch it
If you make Speed per-project (the documented intent), you must add a start/baseline date to ProjectData.ts — which is a data-contract change requiring approval and a contract-doc update.
Build the radar chart (next Phase-1 task)

Create a single component (e.g. frontend/src/features/radar/RadarChart.tsx per the CLAUDE.md intended layout) that takes a RadarScores prop and renders react-chartjs-2's Radar. Register the needed Chart.js scales/elements once. Keep all Chart.js imports inside this file so a future WebGL/d3 swap touches nothing else. Reference the prototype's axis order and tier colors in effectiveness.jsx (cyan fill, green/yellow/red tier dots).

Build the data-entry form & project table

Use react-bootstrap. The form writes a ProjectData (with crypto.randomUUID() for id) via useProjectStore().addProject. The table reads projects and calls selectProject(id) on row click — when a project is selected, score against [selectedProject]; otherwise aggregate over all. Mirror the prototype's "tap row to isolate / tap again to aggregate" UX in effectiveness.jsx. Watch the jsdom Modal pitfall noted in CLAUDE.md §9 when testing.

Wire scores into the UI

Derive scores with useMemo over the store selection: map selected/all ProjectData through computeProjectScores, then computeAggregateScores. Never store derived scores in Zustand — they are pure functions of the project list.

Conventions to respect
One concept per file (no god files). No any, no @ts-ignore without justification. const by default. interface for object shapes. No magic numbers — named constants only. Search the codebase before adding a new function (the scoring helpers already cover the math). Update docs/status.md and docs/versions.md after any code change.

Domain glossary

The vocabulary a newcomer needs to read the formulas and the master plan.

Effectiveness Radar
The five-axis radar chart that is the project's single output.
Axis
One of the five scored dimensions: Speed, Accuracy, Defense, Strength, Endurance. Each 0–100.
Speed
Delivery punctuality vs. committed timeline (target vs. actual date).
Accuracy
How closely outcome matched plan — 50% revenue accuracy + 50% phase (scope) accuracy.
Defense
Security posture: vulnerability count penalized, amplified by breach cost.
Strength
Raw value delivered vs. promised (actual ÷ expected revenue).
Endurance
Compound effect on future delivery: reusable components + intersecting projects.
Tier
Categorical label for any score: HIGH (75–100), MID (45–74), LOW (0–44).
Slip days
Days late = max(0, actual − target). Negative slip (early) clamps to 0.
Planned duration
The denominator Speed scales slip against. Currently fixed at 180 days (see Speed note).
Breach weight
expectedBreachCost / 500000 — the severity multiplier on vuln penalties.
Aggregate scores
Team-level radar: per-axis average across all projects, then overall + tier.
Per-project scores
A single project's radar, used for drill-down / isolation.
Intersecting projects
Other active projects sharing deps, teams, infra, or deliverables.
Reusable components
Artifacts built for reuse: shared libs, APIs, templates, IaC modules.
